# 60 Hz / 120 秒回忆录缓存基准

日期：2026-09-25。PeakReplayLab 0.3.0，Windows x64，.NET 8 Release。
这是纯数据合成测量，不加载 Unity、不启动游戏，不能替代游戏内性能测试。

```powershell
dotnet build PeakReplayLab/tests/ReplayContract/ReplayContract.csproj -c Release --nologo -warnaserror
dotnet run --project PeakReplayLab/tests/ReplayContract/ReplayContract.csproj -c Release --no-build -- --benchmark
```

本次 105 项契约测试通过；编译零警告、零错误。

## 测量方法

每组输入 60 Hz、7,201 帧（包括两端）、120 秒；每人在每一帧有四个动画层，每层两个 clip。
位置及动画时间随帧变化。身份、名称、装扮、动画键使用录制端相同的有界复用池。

每组在独立、禁止内联的方法中创建 `RollingBuffer`，前后执行完整 GC，测量 `GC.GetTotalMemory` 增量。
方法末尾调用 `GC.KeepAlive`，既保证本组缓存未提前释放，也避免上一组局部引用污染下一组结果。
保守计量来自实际 `RollingBuffer.EstimatedBytes`，与 GC 实测内存分开报告。

完整对象组额外包含：

- 256 个静止物品（每件一个节点）、48 个静止箱子，所有帧复用不变的对象状态；对象数组每帧新建。
- 每人 8 个库存栏位、6 个持物手臂节点，并始终记录这组握持节点，作为较重的人物样本。
- 每帧执行实际 `ValidateCapture` 和 `RollingBuffer.Add`；静止对象通过弱引用校验缓存和引用计数估值缓存跳过重复节点遍历。
- 未模拟大量持续变化的物品、每箱复杂节点树或密集使用事件。这些情况会额外增加消耗。

本次构造并校验完整 7,201 帧的累计 CPU 墙钟耗时依次为 493、356、704、685 ms。
这是离线循环总时长，受 JIT、GC、系统负载影响，不能当作 Unity 主线程每帧耗时或性能保证。

256 MiB 默认预算在此输入下可保留 4～8 人的完整两分钟；8 人已接近保守预算。
16 人的重样本必须扩大预算才能达到两分钟，本次 512 MiB 组验证了这一点。
实际场景若有更多节点、频繁移动物品或事件，即使提高预算也不保证固定保留 120 秒。

## 内存、文件和真实性限制

- GC 保留托管内存是合成数据增量，不包含 PEAK 场景、GPU、Unity 模型、渲染副本、采集 API 或播放开销。
- 保守计量会重复计入人物共享字符串和装扮；静止物品/箱子按不可变对象引用只计一次。它用于提前淘汰，不等于操作系统进程内存。
- 256 MiB 是样本预算，不会预分配这么多内存，也不是整个插件的内存硬上限。预算触顶会缩短片段，应观察 F9 的时长与提示。
- F6 后台保存时快照与滚动缓存可同时存活，最差保留旧片段及新一轮样本，另有 JSON、gzip、临时字符串分配。
- RAM 帧始终保留完整、可倒放的状态。Schema 3 文件第一帧全量，后续仅写变化对象和删除键，避免把静止物品序列化 7,200 次；读取时恢复完整帧并复用未变对象引用。
- 单条记录上限 8 MiB UTF-8；压缩文件、展开文本、解码后保守内存分别有 512 MiB 上限。大型重样本保存或读取可能明确拒绝，不能将提高录制预算理解为无限文件支持。
- 60 Hz 是采样目标而不是伪造帧率。每个真实游戏帧最多采一次；30 FPS 实际只有约30个样本/秒，暂停不采集，长卡顿后只记录恢复帧并累计缺失槽位。不会修改游戏物理步长或帧率设置。
- 测试覆盖 60、59.94、120、144、30 FPS 输入、暂停、长停顿、浮点误差及非单调时钟。实际有效帧率仍取决于游戏和机器。
