# 0.4.3 整局持续写入调试

目标：保持现有人物、物品、绳索、放置物和声画采集不变，完整保留一次真实关卡的已采样帧，以定位采集缺失和回放呈现缺失。不是增加全身布娃娃采样，也不表示所有游戏实体已经覆盖。

## 操作

1. 主菜单进入「回忆录」，点「预约下一局整局录制」。也可按 F4 预约；进入真实关卡后自动开始，预约状态随即清除。游戏中按 F4 则从当前时刻开始，不追补此前内容。
2. 正常玩一局，不必每 120 秒按保存。底部显示整局持续落盘时长、写入量、封存段数、待写帧数。F6 仍可单独留精彩片段。
3. 发生卡顿或看到需检查的事件时记下大概本局时间；可按 F9 把当前 CPU 采集统计写到 BepInEx 日志。F9 统计不是全游戏 FPS。
4. 返回主菜单自动停止，等「整局录像已封存」再退出。也可 F4 提前停止。若看到异常提示，不要删除当前会话目录或日志。
5. 回忆录 → 整局调试录像 → 本局 → 对应时间段。每段独立加载地图；目前不跨段无缝播放。

## 文件与容量

目录：`PEAK/BepInEx/PeakReplayLab/DebugRuns/run-<UTC时间>-<唯一编号>/`。

- `manifest.ndjson`：会话开头、封存分段时间／帧数／字节、采样间隙、结束原因及故障信息。
- `segment-000001.peakreplay`：正常封存文件，每段通常约 30 秒。相邻段共享一个真实边界帧，不能简单相加文件帧数来计算采集帧数。
- `*.peakreplay.partial`：当前活动文件或未封存文件，不作为可播放片段展示。现有读取器没有压缩残段恢复功能。

2026-09-26 检查的最新 0.4.2 精彩片段为 **72.166958 秒、4,226 帧、3,125,864 字节（3.126 MB／2.981 MiB）**。按该片段压缩率外推一小时约 156 MB，仅为量级估算；人数、物品、动态绳索与特效，以及分段完整起点，都会改变占用。

同一真实录像通过 0.4.3 整局写入器生成 3 段，总计 **3,791,813 字节（含清单）**，约对应 189 MB／小时。3 段完整读取后逐字段相等，唯一帧 4,226，含重复边界的分段帧数 4,228。原件没有修改。独立完整起点造成额外体积是预期行为；这也不是整局所有场景的容量承诺。

默认单次限制 4 小时／4 GiB。队列最多 360 帧且保守计量不超过 128 MiB（含正在写的帧）；单段解码计量 256 MiB、展开文本 384 MiB，提前分段避免回放读取超限。以上是防护上限，不是预分配内存，也不是整个游戏进程的内存保证。F6 的 256 MiB 滚动预算独立存在。

## 完整性与性能策略

- 不再从 120 秒窗口定时捞取，防止内存预算提前淘汰造成整局缺段；每个已验证采集帧直接送后台队列。
- Unity 主线程只交付引用与已算好的计量值；后台专属线程负责重定位、差分、序列化、压缩、落盘，约每秒刷新流。
- 每段的第一帧是完整状态，不需要早先的“生成”事件。箱子、特效、声音、蘑菇／炮台、气球等绝对时间锚随段统一重定位；角色状态原样保留。
- 不凭空补帧。低帧率或暂停导致的采样间隔会被保留；时长与间隙按原采集游戏时间计算，不是现实秒表。
- 背压／磁盘异常／超限／采集异常均明确停止整局录制，已封存段继续可读，不静默降采样。未写帧数、结束原因和异常用于检查，不把“封存成功”当作所有视觉内容都已正确的证明。
- 本局清单仅做有界元数据检查；点播放时仍通过现有完整录像校验与兼容性保护。流式文件头的时长／帧数为 0，实际数据见段清单，播放时从内容计算。
- 仅本机文件，没有自动上传、麦克风或队友语音。原足迹 Mod 的独立录制／上传设置不变。

## 建议这局覆盖

尽量测试箱子开扣／开盖和真实掉落、拾取／背包存取／切换／消耗／投出；绳子从飞行到固定；放置炮台、弹跳蘑菇、两只绑头气球；悬浮炮、炸弹、火箭背包特效和声音。让一个已放好的东西跨过 30 秒分段和 120 秒滚动边界，再检查后段开头是否仍存在。这里是验收清单，不要求为了测试重复进行危险或妨碍同伴的游戏动作。

玩完保留整局目录和本次 `BepInEx/LogOutput.log`，先不要启动下一局覆盖日志；把大概出问题的时间与对象告诉开发者。检查先看帧／轨道／事件是否存在，再对照回放模型、动画和声画，不仅凭对象数量为 0 推断漏录。
