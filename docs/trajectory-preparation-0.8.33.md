# 上传轨迹前的解析优化：0.8.33

2026-10-15。只修改本地导出准备，不自动发起上传。

## 原因

原先已使用后台任务，但每页依次解压、解码，正常导出需要完整扫描两遍：第一遍确定所有成员和共享时钟，第二遍保留轨迹。每页又调用公共读取接口校验整份可变索引；页数越多，重复校验开销越大。超出分包预算时还会按成员重新读取。

## 实现

- 使用现有独立页读取器建立一次校验的私有索引快照。每页仍执行原来的压缩校验、时间线、身份和解码预算检查。
- 后台同时解码最多 4 页；工作上限为 `min(4, max(1, ProcessorCount - 1))`，不设置 CPU 亲和性。单批页的索引估算解码量合计不超过 128 MiB；解析缓冲、运行时开销和轨迹对象另计，这不是进程内存硬上限。页面处理完及时释放，不把整份录像加入回放缓存。
- 只在工作线程解码数据，按页号和帧时间顺序交给轨迹构建器，保留重叠帧去重、死亡／复活、断线、传送和过关事件原有语义。构建器和进度回调不并发执行。
- 首遍同时收集概览和有预算的完整轨迹；通常直接生成文件，省去第二次解码。保留轨迹超过预算时丢弃该缓冲，完成概览后回退到原有按成员分包流程；写包大小超限也继续按成员拆分，不丢弃队员。
- 取消会传入每个解码任务；并发工作结束后才释放缓冲池或返回异常。输出文件仍使用原来的临时文件、限额与失败清理机制。

不改变采集、录像格式、上传字段、10 Hz 轨迹上限或用户确认上传流程。为保留既有文件验证，本轮仍完整解码页面；专门跳过骨骼、生物等无关字段的轨迹读取器尚未实现。
